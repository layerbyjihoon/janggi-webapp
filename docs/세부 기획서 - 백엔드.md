# 한국 장기 연구 웹앱 세부 기획서 - 백엔드

## 1. 역할 목적

백엔드의 목표는 연구 문서 저장 서버가 아니라 `유저별 단일 Position Graph`와 `position_key 기반 formation lookup`을 안정적으로 제공하는 것이다. 핵심은 저장량보다 `동일 포지션 동일 노드` 원칙을 지키는 것이다.

## 2. 범위

- 유저 단위 Position Graph 저장
- `positions` 조회/생성/업데이트
- `position_edges` 저장과 조회
- `position_formations` 저장과 조회
- 현재 포지션 lookup API

명시적으로 제외:

- move history 기반 formation lookup
- 엔진 분석 처리
- 연구 문서 목록 관리
- 다중 연구 문서 생성

## 3. 핵심 데이터 모델

### PositionNode

- `id`
- `owner_id`
- `position_key`
- `position_data`
- `side_to_move`
- `primary_formation_name`
- 설명 필드가 유지되면 해당 필드

### MoveEdge

- `from_position_id`
- `move`
- `to_position_id`

### PositionFormation

- `position_id`
- `formation_name`
- `formation_family`
- `priority`

## 4. 최소 데이터베이스 구조

### positions

- `id`
- `owner_id`
- `position_key`
- `position_data`
- `primary_formation_name`
- `formation_family`
- `variation`

### position_edges

- `from_position_id`
- `move`
- `to_position_id`

### position_formations

- `position_id`
- `formation_name`
- `formation_family`
- `priority`

필수 인덱스:

- `UNIQUE INDEX positions(owner_id, position_key)`
- `INDEX position_edges(from_position_id)`
- `INDEX position_edges(to_position_id)`
- `INDEX position_formations(position_id)`

유저별 단일 그래프이므로 `owner_id + position_key` 범위에서 동일성을 보장한다.

## 5. 계약 원칙

- 동일 포지션은 동일 Node다.
- move history는 formation lookup 키가 아니다.
- lookup 키는 항상 `position_key`다.
- 해시는 검색 최적화용으로만 쓰고 canonical representation 기반 동일성 검증 경로를 남긴다.
- edge는 PositionNode 간 연결 정보이며 formation metadata는 PositionNode에 귀속한다.

## 6. 우선 구현 API

### 현재 포지션 lookup

- 입력: `owner_id`, `position_key`
- 출력: PositionNode와 formation metadata

### Position upsert

- 입력: `owner_id`, `position_key`, `position_data`
- 동작: 동일 key면 기존 노드 반환, 없으면 생성

### Edge upsert

- 입력: `from_position_id`, `move`, `to_position_id`
- 동작: 중복 edge 방지

### Formation metadata 조회/수정

- 입력: `position_id`
- 출력: `primary_formation_name`, `formation_names[]`, 계층 메타데이터

## 7. 우선 결정해야 할 사안

### canonical serialization 형식

- board 90칸 순회 순서
- 기물 enum 값
- `side_to_move` 표현

이 셋이 안 정해지면 FE와 BE는 같은 포지션을 공유할 수 없다.

### owner scope

- 전역 그래프인지
- 유저별 독립 그래프인지

이번 요구사항은 유저별 단일 그래프이므로 우선 `owner_id` 기준 분리를 전제로 한다.

### 설명 필드 유지 여부

- PositionNode에 설명을 둘지
- Formation metadata에 설명을 둘지

이 결정은 UX와 API 응답 구조에 직접 영향을 준다.

## 8. 프론트엔드와의 핸드오프 기준

- canonical serialization golden fixture 제공
- 동일 포지션 샘플 2경로 transposition fixture 제공
- lookup 성공/미등록/오류 응답 예제 제공
- PositionNode 응답 예제 제공

## 9. QA 관점의 필수 검증 포인트

- 같은 포지션이 중복 row 없이 재사용되는가
- 서로 다른 경로가 같은 PositionNode로 합쳐지는가
- lookup 키가 sequence string이 아니라 `position_key`인가
- formation metadata가 PositionNode 기준으로 조회되는가
- 미등록 포지션이 오류 없이 구분되는가

## 10. 완료 기준

- FE가 실제 API로 `position_key` lookup을 검증할 수 있다.
- 동일 포지션 중복 생성이 차단된다.
- edge 저장과 formation metadata 저장이 분리돼 있다.
- canonical serialization 규칙이 문서와 테스트에 고정돼 있다.

## 11. 에스컬레이션 조건

- `position_key` 생성 규칙이 반복 변경될 때
- `owner_id + position_key` uniqueness가 깨질 때
- sequence history 기반 조회 요구가 재유입될 때
- transposition 병합이 구현 중간에 생략되려 할 때
