# 한국 장기 연구 웹앱 세부 기획서 - 프론트엔드

## 1. 역할 목적

프론트엔드의 목표는 `수 적용 -> 새 포지션 계산 -> position_key 생성 -> Position Graph lookup -> 포진명 표시` 루프를 안정적으로 닫는 것이다. 이번 수정 이후 우선순위는 아래 순서로 고정한다.

- 1순위: board state와 position serialization 일치성
- 2순위: graph lookup과 formation metadata 표시
- 3순위: 엔진 패널 비동기 연결

## 2. 구현 범위

- 장기판 렌더링과 합법 수 적용
- 현재 포지션 canonical serialization
- `position_key` 생성
- Position Graph lookup 결과 반영
- 현재 PositionNode의 formation metadata 표시
- 미등록 포지션 상태 표시
- Web Worker 기반 엔진 패널 연결

## 3. 프론트엔드 모듈 경계

### 보드 도메인

- 현재 국면 렌더링
- 합법 수 반영
- 수 적용 후 새 board state 산출

### Position 직렬화 계층

- `board[90] + side_to_move` 기준 canonical serialization
- 동일 상태에 대해 항상 같은 표현 산출
- 해시 입력용 원본 문자열 생성

### Position Key 계층

- canonical representation 기반 `position_key` 생성
- lookup용 key와 디버그용 원본 표현 연동

### Graph Lookup 계층

- 현재 `position_key`로 PositionNode 조회
- 조회 결과를 UI 상태로 변환
- 미등록 포지션 상태 판별

### Formation Metadata 패널

- `primary_formation_name` 표시
- `formation_names[]` 보조 노출
- 설명 필드가 유지되면 표시/편집

### 엔진 어댑터

- Worker 초기화
- 현재 포지션 전달
- 분석 시작, 중지, 오류 상태 수신

## 4. 구현 순서

### Step 1. Position 계산 루프 구축

- 수 적용 후 board state 갱신
- canonical serialization 생성
- `position_key` 생성
- 로컬 mock graph lookup 연결

완료 기준:

- 같은 포지션은 같은 key를 만든다.

### Step 2. 포진명 표시 루프 연결

- lookup 결과를 메타데이터 패널에 반영
- 등록/미등록 상태 구분
- 별칭 노출 처리

완료 기준:

- 사용자가 한 수를 둔 직후 현재 포지션의 포진명 유무를 볼 수 있다.

### Step 3. Transposition 대응

- 서로 다른 수순으로 같은 포지션에 도달하는 fixture 적용
- lookup 결과가 동일 노드를 참조하는지 확인

완료 기준:

- 경로가 달라도 화면은 동일 PositionNode 메타데이터를 보여준다.

### Step 4. 엔진 패널 연결

- Worker 초기화
- 분석 시작/중지
- 포진 lookup 상태와 엔진 상태 분리

완료 기준:

- 엔진 패널 오류가 포진 lookup UI를 깨지 않는다.

## 5. 데이터 계약 요구사항

프론트엔드는 아래 필드가 고정돼야 안정적으로 구현할 수 있다.

- `position_key`
- `position_data`
- `side_to_move`
- `primary_formation_name`
- `formation_names[]`
- 설명 필드가 유지되면 해당 필드
- outgoing edge 목록
- 현재 포지션 ID

## 6. 구현 난이도 상위 항목

### FE/BE serialization 일치성

- 같은 판 상태에서 같은 canonical string을 만들어야 한다.
- enum, 보드 순회 순서, side_to_move 표현이 하나라도 다르면 lookup이 깨진다.

### Transposition 처리

- FE는 경로가 아니라 현재 포지션을 기준으로 UI를 갱신해야 한다.
- 이전 이동 이력 캐시가 메타데이터 표시를 오염시키면 안 된다.

### 미등록 포지션 상태

- lookup miss를 오류와 구분해야 한다.
- 로딩, 실패, 미등록 세 상태를 명확히 나눠야 한다.

### 엔진 패널과 포진 lookup 분리

- 두 기능 모두 현재 포지션을 쓰지만 상태 머신은 분리해야 한다.

## 7. 백엔드 의존성

- canonical serialization 규칙 확정
- `position_key` 생성 규칙 확정
- PositionNode 응답 형식 확정
- formation metadata 필드 확정

## 8. UX/UI 의존성

- 포진명, 별칭, 미등록 상태 노출 규칙
- transposition 시각 표현 방식
- 설명 필드 유지 여부
- 엔진 패널 분리 방식

## 9. 프론트엔드 완료 기준

- 사용자가 한 수를 두면 새 포지션이 계산된다.
- 현재 포지션으로 `position_key` lookup이 동작한다.
- 등록 포지션이면 `primary_formation_name`이 보인다.
- 미등록 포지션이면 오해 없는 상태가 보인다.
- 다른 경로로 같은 포지션에 도달해도 동일한 metadata가 보인다.

## 10. 구현 중단 및 에스컬레이션 조건

- FE와 BE의 `position_key`가 다를 때
- lookup miss와 시스템 오류가 구분되지 않을 때
- sequence history 기반 포진 표시 요구가 다시 들어올 때
- transposition fixture에서 동일 노드 재사용이 깨질 때
