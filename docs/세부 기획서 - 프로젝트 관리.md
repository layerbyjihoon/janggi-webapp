# 한국 장기 연구 웹앱 세부 기획서 - 프로젝트 관리

## 1. 문서 목적

이 문서는 기존 [제품 기획서](C:\Users\john9\Private_Project\제품 기획서.md)와 [서비스 아키텍처](C:\Users\john9\Private_Project\docs\서비스 아키텍처.md)를 실제 전달 가능한 실행 계획으로 다시 정렬하기 위한 총괄 관리 문서다. 이번 수정의 핵심은 `연구 문서/분기 트리` 모델을 버리고 `유저당 단일 Position Graph` 모델로 전환하는 것이다.

## 2. 이번 수정으로 확정할 핵심 범위

- 유저는 여러 연구 문서를 생성하지 않는다.
- 유저마다 하나의 장기 Position Graph만 가진다.
- 포진 이름은 `move history`가 아니라 `현재 position`에 귀속한다.
- 사용자가 수를 둘 때마다 현재 판 상태에서 `position_key`를 생성하고, 해당 PositionNode의 포진 메타데이터를 조회한다.
- 서로 다른 착수 순서로 동일 포지션에 도달하면 기존 PositionNode를 재사용한다.
- UI는 현재 PositionNode의 `primary_formation_name`을 즉시 표시한다.

## 3. 변경 영향 요약

이번 수정은 단순 문구 변경이 아니라 저장 모델과 사용자 흐름 자체를 바꾼다.

- `새 연구 생성 / 최근 연구 재개` 흐름 제거
  기존 문서의 문서 목록, 재개, 마지막 열람 위치 개념이 대부분 불필요해진다.
- `문서 트리 저장`에서 `Position Graph 저장`으로 전환
  저장 단위가 연구 문서가 아니라 유저 소유 그래프와 현재 활성 포지션이 된다.
- `분기 이름/설명` 중심 UX에서 `현재 포지션의 포진명 표시/관리` 중심 UX로 전환
  이름이 수순이 아니라 포지션에 귀속되므로 화면 정보 구조가 달라진다.
- `move history`를 포진 판별 키로 사용하지 않음
  FE와 BE 모두 매 수마다 `apply(move) -> serialize(position) -> position_key lookup` 경로를 기준으로 설계해야 한다.

## 4. 요구사항 동결 게이트

### Gate A. 도메인 해석 동결

아래 항목이 합의되기 전에는 세부 설계와 구현을 잠그지 않는다.

- 유저 단위 단일 그래프의 범위
- 포지션 이름 외에 설명 필드를 유지할지 여부
- 현재 활성 포지션의 저장 방식
- UI에서 보여줄 포진명 구조가 `primary_formation_name` 단일 노출인지, `formation_names[]` 다중 노출인지

### Gate B. Position Key 동결

아래 항목이 고정되기 전에는 FE/BE 계약을 잠그지 않는다.

- canonical board serialization 규칙
- `board_state + side_to_move` 포함 범위
- 해시 사용 시 원본 canonical representation 보관 여부
- 동일성 검증 방식

## 6. 단계별 전달 계획

일정은 날짜가 아니라 산출물 완료 기준으로 관리한다.

### Phase 0. 도메인 재정의

목표는 `문서형 연구 모델`에서 `Position Graph 모델`로 완전히 전환하는 것이다.

- 유저당 단일 그래프 정책 확정
- 새 연구/최근 연구 관련 잔존 요구 제거
- 포진명, 설명, 메타데이터의 귀속 단위 확정

완료 기준:

- 전 역할 문서에서 저장 단위를 `문서` 대신 `PositionNode/Graph` 기준으로 동일하게 사용한다.
- QA가 요구사항을 테스트 문장으로 다시 적을 수 있다.

### Phase 1. Position Graph 계약 동결

목표는 구현 전에 데이터 동일성 기준을 잠그는 것이다.

- `PositionNode`, `MoveEdge`, `position_formations` 구조 확정
- canonical serialization 규칙 확정
- `position_key` 생성 규칙 확정
- transposition 재사용 규칙 확정

완료 기준:

- FE와 BE가 동일 포지션에 대해 같은 `position_key`를 산출한다.
- 같은 포지션으로 수렴하는 2개 경로 예제로 node 중복 생성이 없음을 검증한다.
- QA가 lookup/중복 방지 테스트를 작성할 수 있다.

### Phase 2. UX/UI 상세화

목표는 단일 그래프 작업 공간을 이해 가능한 UI로 바꾸는 것이다.

- 단일 그래프 진입 화면
- 현재 포지션과 포진명 표시 영역
- graph 탐색 방식
- 미등록 포지션 상태
- formation metadata 관리 패널

완료 기준:

- FE가 추가 질문 없이 상태 전이를 구현할 수 있다.
- 포진명 노출 규칙과 미등록 상태가 명확하다.

### Phase 3. 세로 슬라이스 구현

목표는 사용자가 한 수를 두고 포진명을 즉시 확인하는 핵심 루프를 먼저 닫는 것이다.

- 현재 포지션 렌더링
- 수 적용
- 새 포지션 계산
- `position_key` 생성
- Position Graph lookup
- `primary_formation_name` 표시

완료 기준:

- 서로 다른 두 수순이 동일 포지션에 도달하면 같은 PositionNode가 재사용된다.
- 미등록 포지션과 등록 포지션이 즉시 구분된다.
- 엔진 분석과 포진 lookup이 서로의 상태를 오염시키지 않는다.

### Phase 4. 안정화와 릴리즈 게이트

목표는 graph 저장, lookup, transposition에서 발생하는 상위 리스크를 줄이는 것이다.

- canonical serialization 회귀 검증
- position_key 중복/충돌 방지 검증
- edge 저장 무결성 검증
- 미등록 포지션 처리 검증
- 회귀 테스트

완료 기준:

- P1 결함이 남아 있지 않다.
- 동일 포지션 중복 노드 생성이 재현되지 않는다.
- lookup 지연이 허용 범위 안에 있다.

## 7. 크리티컬 패스

1. Gate A 도메인 해석 동결
2. Gate B position_key 규칙 동결
3. Position Graph 스키마 고정
4. FE/BE position lookup 세로 슬라이스 통합

가장 위험한 지점은 `position_key 규칙`, `transposition 중복 방지`, `FE/BE 직렬화 일치성`이다. 이 셋이 흔들리면 전 역할 재작업이 발생한다.

## 8. 병렬화 가능한 영역

- UX/UI는 Gate A 이후 단일 그래프 작업 공간과 포진 표시 UX를 먼저 설계할 수 있다.
- FE는 실제 API 없이도 로컬 position serialization과 graph lookup mock으로 화면 루프를 만들 수 있다.
- BE는 formation metadata CRUD를 lookup 경로와 분리해 병행 구현할 수 있다.
- QA는 transposition 샘플 포지션 세트를 먼저 고정할 수 있다.

## 9. 의존성 맵

### PM -> 전 팀

- 변경 요구가 다시 들어오면 `문서형 저장`으로 되돌아가지 않도록 용어를 잠가야 한다.

### 백엔드 -> 프론트엔드

- FE는 BE가 정의한 canonical serialization 규칙과 동일한 규칙을 써야 한다.
- `position_key` 정의가 늦거나 바뀌면 FE 보드 상태 관리와 lookup 코드가 모두 재작업된다.

### UX/UI -> 프론트엔드

- 포진명 단일 노출, 다중 별칭 노출, 미등록 상태 표현이 정해져야 FE가 패널 구조를 잠글 수 있다.

### 프론트엔드 -> QA

- QA는 FE가 수 적용 후 lookup 결과를 어떤 타이밍에 노출하는지 알아야 검증 지점을 잡을 수 있다.

### 백엔드 -> QA

- transposition 예제 데이터와 동일 포지션 재사용 규칙이 없으면 QA가 중복 저장 검증을 못 한다.

## 10. 상위 리스크와 대응

### Risk 1. FE/BE position_key 불일치

- 영향: lookup 실패, 포진명 오표시
- 조기 신호: 같은 판 상태에서 서로 다른 key 산출
- 대응: 공용 fixture와 golden test 세트 고정
- 에스컬레이션 기준: 동일 포지션 샘플 1건이라도 key mismatch가 발생할 때

### Risk 2. 동일 포지션 중복 저장

- 영향: graph 무결성 붕괴, 포진명 충돌
- 조기 신호: 같은 canonical position에 대해 node row가 2개 이상 생성됨
- 대응: `position_key UNIQUE INDEX`와 insert/upsert 규칙 고정
- 에스컬레이션 기준: 중복 row가 테스트나 staging에서 1건이라도 재현될 때

### Risk 3. 문서형 UX 잔재

- 영향: 사용자 흐름 혼선, 설계 재작업
- 조기 신호: 새 연구, 최근 연구, 문서 제목 같은 개념이 화면에 남아 있음
- 대응: UX 리뷰에서 문서형 용어 제거 체크리스트 사용
- 에스컬레이션 기준: 역할 문서 2개 이상에 문서형 흐름이 잔존할 때

### Risk 4. formation metadata 모델 과복잡화

- 영향: MVP 일정 붕괴
- 조기 신호: family, variation, subvariation까지 동시에 강제하려 함
- 대응: MVP는 `primary_formation_name`과 `formation_names[]`를 우선
- 에스컬레이션 기준: Gate B 이전에 계층 메타데이터가 필수 조건으로 바뀔 때

### Risk 5. move history 의존 로직 재유입

- 영향: 핵심 도메인 원칙 위반
- 조기 신호: sequence string으로 포진 조회하려는 설계가 다시 등장
- 대응: lookup 키는 항상 `position_key`로 고정
- 에스컬레이션 기준: 설계 문서나 코드에서 sequence lookup이 발견될 때

## 11. 비상 계획과 우회 경로

### 시나리오 A. formation metadata 범위가 커지는 경우

- 우회안: `primary_formation_name` 단일 노출과 별칭 배열만 먼저 제공한다.

### 시나리오 B. position_key 해시 충돌 우려가 큰 경우

- 우회안: 해시는 검색 최적화용으로만 쓰고 canonical representation을 함께 저장한다.

### 시나리오 C. graph 탐색 UX가 과도하게 복잡한 경우

- 우회안: MVP는 현재 포지션, 직접 연결된 이웃 포지션, 현재 포진명 표시만 우선 제공한다.

### 시나리오 D. 엔진 통합이 늦어지는 경우

- 우회안: 엔진 패널은 독립 상태 머신으로 유지하고 포진 lookup 루프를 먼저 닫는다.

## 12. 릴리즈 게이트

- 사용자가 수를 두면 즉시 새 포지션이 계산된다.
- 같은 포지션은 항상 같은 `position_key`와 같은 PositionNode에 매핑된다.
- 등록 포지션이면 `primary_formation_name`이 즉시 보인다.
- 미등록 포지션이면 오탐 없이 미등록 상태가 보인다.
- move history 없이도 formation lookup이 동작한다.

## 13. 다음 조정 액션

1. PM이 문서형 요구를 모두 제거한 변경 로그를 확정한다.
2. BE가 canonical serialization과 `position_key` golden fixture를 만든다.
3. FE가 그 fixture로 동일 key 생성 테스트를 붙인다.
4. QA가 transposition 재사용 시나리오를 P1 회귀로 잠근다.
