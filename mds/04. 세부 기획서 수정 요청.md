# 장기 포진 Position Graph 설계 프롬프트

장기의 포진 및 초반 형태를 저장하고 탐색할 수 있는 **포지션 기반 그래프(Position Graph)** 구조를 설계하고 구현해줘.

## 핵심 요구사항

이 시스템에서 포진 이름은 **착수 이력(move history)이 아니라 현재 장기 포지션(position)에 귀속**된다.

따라서 사용자가 어떤 순서로 말을 움직였는지는 포진 판별에 사용하지 않는다.

사용자가 매 수를 둘 때마다:

1. 현재 포지션에 착수를 적용한다.
2. 새로운 장기 포지션을 계산한다.
3. 해당 포지션의 고유 `position_key`를 생성한다.
4. Position Graph에서 동일한 포지션을 조회한다.
5. 해당 포지션에 등록된 포진 이름을 반환한다.
6. 서로 다른 착수 순서로 동일한 포지션에 도달하더라도 하나의 PositionNode만 사용한다.

## 기본 구조

포지션을 Node로 표현하고 착수를 Edge로 표현한다.

```text id="2vgx92"
PositionNode
- id
- position_key
- position_data
- formation_names[]
- primary_formation_name
- outgoing_edges[]

MoveEdge
- from_position_id
- to_position_id
- move
```

예:

```text id="wrql5s"
START
  │ 착수 A
  ▼
P1
  │ 착수 B
  ▼
P2 [기본 포진]
  │ 착수 C
  ▼
P3
  │ 착수 D
  ▼
P4 [귀마 포진]
```

## Transposition 처리

서로 다른 착수 순서를 통해 동일한 포지션에 도달할 수 있다.

```text id="bn2z2c"
Path A ─────┐
            ▼
         Position X
            ▲
Path B ─────┘
```

이 경우 Position X를 중복 생성하지 않는다.

두 경로가 동일한 `PositionNode`를 참조하도록 한다.

핵심 원칙:

```text id="2jy5kq"
동일한 장기 포지션 = 동일한 Node
```

착수 순서가 다르다는 이유로 새로운 노드를 만들지 않는다.

## Position Key

현재 장기판 상태를 기반으로 canonical position key를 생성한다.

최소한 다음 정보를 포함한다.

* 모든 기물의 위치
* 각 기물의 종류
* 각 기물의 진영
* 현재 둘 차례

예:

```text id="d4m6m3"
position_key =
board_state
+ side_to_move
```

장기 규칙상 동일 포지션 판정에 추가 상태가 필요하다면 해당 상태도 포함한다.

position key는 문자열 직렬화 방식 또는 hash 방식으로 구현할 수 있다.

예:

```text id="8lrp7w"
canonical_board_string
→ hash
→ position_key
```

빠른 검색이 필요하면 Zobrist Hash와 유사한 방식의 해시를 사용할 수 있다.

단, 해시는 검색 최적화 용도로 사용하고 실제 동일성 검증에는 canonical board representation을 함께 사용할 수 있도록 설계한다.

## 포진 정보

포진 정보는 착수나 history가 아니라 PositionNode에 저장한다.

```text id="jg88kt"
PositionNode {
    position_key
    formation_names[]
    primary_formation_name
}
```

하나의 포지션이 여러 분류에 해당할 수 있으므로 하나의 이름만 강제하지 않는다.

예:

```json id="n0pdc5"
{
  "formation_names": [
    "귀마",
    "귀마 계열 포진"
  ],
  "primary_formation_name": "귀마"
}
```

필요하다면 다음과 같은 계층 구조를 추가할 수 있다.

```text id="iw483m"
formation_family
formation
variation
subvariation
```

예:

```text id="wqas3t"
귀마 계열
└─ 귀마
   └─ 특정 변형
```

UI에서 하나의 이름만 보여줘야 한다면 가장 구체적인 포진 이름을 `primary_formation_name`으로 사용한다.

## Runtime 동작

사용자가 장기말을 움직일 때 다음 흐름으로 처리한다.

```text id="y9vxgv"
current_position
      ↓
apply(move)
      ↓
new_position
      ↓
generate_position_key()
      ↓
PositionGraph lookup
      ↓
PositionNode
      ↓
formation metadata 반환
```

즉 매 착수마다 현재 판 전체를 기준으로 포진을 다시 판별한다.

착수 sequence 문자열을 포진 조회 key로 사용하지 않는다.

잘못된 방식:

```text id="c2hshy"
formation_lookup[
    "착수A 착수B 착수C 착수D"
]
```

올바른 방식:

```text id="z36lnf"
formation_lookup[
    position_key
]
```

## History

포진 판별을 위한 move history는 저장하지 않는다.

현재 게임 상태에서 필요한 핵심 정보는 다음 두 가지뿐이다.

```text id="dai0hu"
current_position
current_position_key
```

각 착수 후 새로운 position key를 계산하고 해당 PositionNode를 조회한다.

## 데이터베이스 구조

최소한 다음 테이블을 고려한다.

### positions

```text id="pu419l"
id
position_key UNIQUE
position_data
primary_formation_name
formation_family
variation
```

### position_edges

```text id="8gjz93"
from_position_id
move
to_position_id
```

### position_formations

하나의 포지션에 여러 포진 이름을 연결하려면 별도 테이블을 사용한다.

```text id="uazko3"
position_id
formation_name
formation_family
priority
```

추천 인덱스:

```text id="dit73i"
UNIQUE INDEX positions(position_key)

INDEX position_edges(from_position_id)
INDEX position_edges(to_position_id)

INDEX position_formations(position_id)
```

## Position 직렬화

장기판을 항상 같은 순서로 직렬화해서 동일한 판 상태가 동일한 position key를 생성하도록 한다.

예를 들어 9×10 장기판을 일정한 순서로 읽는다.

```text id="gej6m0"
상단 좌측
→ 오른쪽
→ 다음 행
→ ...
→ 하단 우측
```

각 칸을 다음과 같이 표현할 수 있다.

```text id="f20yfn"
빈칸 = 0

초:
차, 포, 마, 상, 사, 왕, 졸

한:
차, 포, 마, 상, 사, 왕, 병
```

실제 내부 구현에서는 숫자 enum을 사용하는 것을 권장한다.

예:

```text id="1shtge"
0 = EMPTY

1 = CHO_KING
2 = CHO_ROOK
3 = CHO_CANNON
4 = CHO_KNIGHT
5 = CHO_ELEPHANT
6 = CHO_GUARD
7 = CHO_PAWN

11 = HAN_KING
12 = HAN_ROOK
13 = HAN_CANNON
14 = HAN_KNIGHT
15 = HAN_ELEPHANT
16 = HAN_GUARD
17 = HAN_PAWN
```

그리고:

```text id="g26xm7"
board[90]
+
side_to_move
```

를 canonical serialization 대상으로 사용한다.

## 그래프 설계 원칙

다음 원칙을 반드시 지킨다.

1. Position이 시스템의 핵심 Entity다.
2. Move는 Position과 Position을 연결하는 Edge다.
3. 동일한 Position을 중복 저장하지 않는다.
4. 서로 다른 착수 순서로 동일한 Position에 도달하면 기존 PositionNode를 재사용한다.
5. 포진 이름은 PositionNode에 귀속한다.
6. 포진 판별에 move history를 사용하지 않는다.
7. 현재 position_key만으로 포진을 조회할 수 있어야 한다.
8. 하나의 포지션에 여러 포진 명칭을 등록할 수 있다.
9. `position_key`에 UNIQUE INDEX를 둔다.
10. UI에서는 사용자가 한 수 둘 때마다 현재 PositionNode의 `primary_formation_name`을 즉시 표시한다.

## DAG 여부

전체 장기 포지션 공간은 같은 포지션으로 다시 돌아오는 착수가 가능할 수 있으므로 반드시 DAG라고 가정하지 않는다.

자료구조는 일반적인 **Directed Position Graph**로 구현한다.

```text id="2jb6ws"
Position A
 ├─ Move → Position B
 ├─ Move → Position C
 └─ Move → Position D
```

그리고 서로 다른 경로가 같은 포지션으로 합쳐질 수 있다.

```text id="fj74se"
Position B ─┐
            ├→ Position X
Position C ─┘
```

따라서 핵심은 DAG 자체가 아니라:

```text id="22jrur"
position_key
      ↓
unique PositionNode
      ↓
formation metadata
```

구조다.

## 최종 목표

사용자가 장기판에서 말을 한 수 움직일 때마다:

```text id="8gqz41"
착수
 ↓
새 장기판 상태 생성
 ↓
position_key 생성
 ↓
Position Graph 검색
 ↓
등록된 포진 존재?
 ├─ YES → 포진 이름 표시
 └─ NO  → 미등록 포지션
```

이 흐름이 빠르게 실행되도록 구현해줘.

데이터 모델, DB schema, position serialization, position key 생성, graph lookup, transposition 처리, 포진 metadata 관리, move 적용 로직을 각각 분리해서 설계해줘.
