# Position Graph 전환 작업 운영 가이드

## 목적

이 문서는 `tasks` 하위 역할별 task 패키지를 병렬로 실행할 때 충돌을 줄이고, 핵심 의존성과 통합 시점을 고정하기 위한 운영 기준이다.

## 로컬 우선 처리 항목

- 프로젝트 관리 스트림이 `Gate A. 도메인 해석 동결`과 `Gate B. Position Key 동결`을 먼저 잠근다.
- 백엔드 스트림이 canonical serialization 규칙과 `position_key` fixture 포맷을 먼저 제안한다.
- 이 두 항목이 잠기기 전에는 프론트엔드와 QA가 실제 계약을 확정하지 않는다.

## 병렬 실행 가능한 작업 스트림

| 스트림 | 주 오너 | 쓰기 범위 | 선행 조건 | 기대 산출물 |
|---|---|---|---|---|
| 프로젝트 관리 | PM | `tasks/프로젝트 관리` | 없음 | Gate 결정, 리스크 로그, 릴리즈 게이트 |
| UX/UI | UX 리드 | `tasks/UXUI` | Gate A | 와이어프레임, 상태 명세, FE/QA 핸드오프 |
| 백엔드 | BE 리드 | `tasks/백엔드` | Gate A, Gate B 초안 | 스키마, API 계약, fixture, 중복 방지 규칙 |
| 프론트엔드 | FE 리드 | `tasks/프론트엔드` | Gate A, Gate B 초안, UX 초안 | position loop, metadata UI, 엔진 분리 구현 계획 |
| QA | QA 리드 | `tasks/QA` | Gate B 초안, FE/BE 응답 예제 | fixture 기반 검증 계획, 회귀 세트, 릴리즈 체크 |

## 출력 계약

- 프로젝트 관리는 용어 동결, 의사결정 로그, 통합 체크포인트를 유지한다.
- UX/UI는 화면 상태와 라벨 정의를 텍스트만 봐도 FE가 구현 가능한 수준으로 적는다.
- 백엔드는 `position_key` 산출 근거와 응답 예제를 문서화한다.
- 프론트엔드는 상태 전이와 비동기 분리 규칙을 명확히 적는다.
- QA는 같은 fixture를 기준으로 FE와 BE를 함께 검증할 수 있는 시나리오를 만든다.

## 의존성과 대기 지점

### Checkpoint 1. Gate A

- 프로젝트 관리 `TASK-01` 완료가 기준이다.
- UX/UI, 백엔드, 프론트엔드는 문서형 잔재 제거와 단일 Position Graph 용어를 이 시점부터 고정한다.

### Checkpoint 2. Gate B 초안

- 백엔드 `TASK-01`이 canonical serialization, `position_key`, fixture 포맷 초안을 제시한다.
- 프론트엔드 `TASK-01`, QA `TASK-01`은 이 초안을 입력으로 사용한다.

### Checkpoint 3. 세로 슬라이스 통합

- 백엔드 `TASK-03`, 프론트엔드 `TASK-02`, UX/UI `TASK-03`, QA `TASK-02`가 만나는 지점이다.
- lookup 성공, 미등록, 오류 상태가 서로 같은 용어와 상태 코드를 써야 한다.

### Checkpoint 4. 릴리즈 게이트

- QA `TASK-04`와 프로젝트 관리 `TASK-04`가 P1 결함, key mismatch, transposition 실패 여부를 최종 확인한다.

## 충돌 방지 규칙

- `position_key` 정의 충돌은 프로젝트 관리가 조정하되 최종 기술 오너는 백엔드다.
- 포진명, 별칭, 미등록 상태 노출 충돌은 UX/UI가 결정하고 프론트엔드가 구현에 반영한다.
- 테스트 fixture 충돌은 QA가 기준본을 관리하되, 원본 직렬화 규칙은 백엔드 문서를 따른다.
- 같은 파일을 두 스트림이 동시에 수정하지 않는다. 역할별 쓰기 범위는 각 폴더로 한정한다.

## 통합 체크리스트

- [ ] Gate A가 문서로 동결되었다.
- [ ] Gate B 초안이 FE, BE, QA 모두에게 공유되었다.
- [ ] lookup 성공, 미등록, 오류 응답 예제가 하나의 계약으로 정리되었다.
- [ ] transposition fixture가 FE, BE, QA에서 동일하게 사용된다.
- [ ] 엔진 상태와 formation lookup 상태가 분리된 것으로 검증되었다.

## 최고 위험과 대응

- 최고 위험은 FE와 BE의 canonical serialization 불일치다.
- 대응은 백엔드가 fixture와 원본 canonical representation을 먼저 고정하고, 프론트엔드와 QA가 그 fixture를 그대로 재사용하는 것이다.

## 부분 완료 시 우회 경로

- Gate B가 늦어지면 프론트엔드는 mock lookup까지 진행하고 실제 API 결선은 보류한다.
- formation metadata 범위가 커지면 `primary_formation_name`과 `formation_names[]`만 MVP에 남긴다.
- graph 탐색 UX가 복잡하면 현재 포지션과 인접 포지션만 우선 노출한다.
